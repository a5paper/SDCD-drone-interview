## Assumptions

For the sake of the first Task I made several assumptions:

1. Simple physics — I assume the drone moves at either a constant speed or 0, since I don't want to deal with acceleration.
   The command (Vx, Vy) is split into a unit direction and a speed: speed = min(length, 1) × max speed. A diagonal command therefore moves at max speed, not √2 × max speed.
2. World Simulation — For the sake of this simulation I am making it all in the same project and creating an in-code separation between the drone simulation and the world simulation.
3. The world doesn't particularly matter — Since I want to simulate a drone, and not a lively world, I am going to put minimal effort into the camera, much like the question asks.
4. Build environment — This project builds and runs on Ubuntu 24.04 (also on WSL) and on Windows 10/11 with MSVC (Visual Studio 2022 or 2026). Linux uses apt packages and GCC; Windows uses vcpkg and the PowerShell twins of the scripts.

## Tradeoffs

- **JPEG over H.264.** Each frame stands alone, so a lost packet costs one frame, not a smear until the next keyframe. The chunk protocol is our own and small. Cost: about 5-10x more bandwidth. An `ffmpeg` child process hides loss handling and copies raw frames between processes. libav is several times more code. H.264 from a hardware encoder is the production upgrade, and only `VideoStreamer` and the GCS decoder would change.
- **Separate telemetry stream.** Telemetry keeps arriving when video is lost, and its rate is independent. Each packet carries the latest `frame_id`, and the GCS shows each frame with its matching telemetry. Cost: a small matching buffer on the GCS. No clock sync is needed.
- **UDP everywhere.** Only the newest frame, state and command matter. TCP retransmits stale data and its head-of-line blocking adds latency when the link is bad. Commands are resent by the GCS, so a lost one is replaced. OS difference: sending to a port nobody listens on counts as a send failure on Linux (`ECONNREFUSED`), but never fails on Windows (the error, `WSAECONNRESET` 10054, appears only on a later `recv`), so "Video/Telemetry send failures" stay 0 on Windows with no GCS running. The loop is unaffected on both.
- **No retransmission.** An incomplete frame is dropped when a newer one arrives. Loss lowers the frame rate and never stalls the video.
- **FEC as a strategy, XOR parity by default.** The scheme is chosen in `config/drone.ini` (`[video]`: `fec = none|xor`, `fec_group_size`), and each chunk says which scheme it uses, so the receiver picks the matching decoder by itself. XOR parity rebuilds one lost chunk per group with no retransmit. Measured live with `tc netem` at 5 % loss: 53 % of frames shown without FEC, 84 % with one parity chunk per frame (about 8 % more bandwidth), 94 % with groups of 5 (about 23 % more). Two losses in one group still drop the frame. Reed-Solomon would recover more and fits in as one more strategy.
- **Datagrams under the MTU.** No IP fragmentation. If one fragment were lost, the whole datagram would be lost.
- **Protobuf.** Cross-language (C++ and Python) with no manual byte packing. Cost: a few bytes per message. The version is pinned to 3.21.12 on both OSes (apt on Ubuntu, a vcpkg `overrides` entry on Windows), so one `protoc` and one Python `protobuf==4.21.12` serve both. The price is an old library that vcpkg compiles from source on first install.
- **Single-threaded 60 Hz loop.** Simple and deterministic, with no locks. Rendering and encoding run every 2nd tick, so video is 30 fps, a mean frame gap of 33.3 ms; telemetry is every 6th tick (10 Hz). Cost: about 460-580 KiB/s of video (measured), and the render must fit in the tick budget. 30 fps needs a loop rate divisible by 30: a 50 Hz loop could only give 25 fps, or uneven 20/40 ms frame gaps.
- **Deadline-based loop timing.** Each tick waits for the previous deadline plus one period, so a late wake-up is absorbed by the next tick instead of accumulating. The first version waited one period from "now" and drifted: 29.5 fps on Linux, 16-27 fps on Windows. If a tick is more than one period late the deadline restarts from now, so there is no catch-up burst. On Windows `std::this_thread::sleep_until` wakes on a ~15.6 ms timer by default, so the loop clock raises the timer resolution to 1 ms (`timeBeginPeriod(1)`) for its lifetime. Target: a mean frame gap of 33.3 ± 0.5 ms with a typical p99 of about 3 ms. Most runs meet it; one Windows run (33.87 ms mean, p99 10.8 ms) and one Linux run (34.19 ms mean) did not, because of host scheduler stalls: a bare sleep loop on the same machine overshoots by up to 99 ms (see the measured numbers in `code-map.md`).
- **Cars as a structure of arrays.** About 4,500 cars fill every lane and wrap around at the world edge, so nothing is allocated or deleted at runtime and a car's index is its persistent ID. Cars are stored per road axis as separate float arrays, so the update reads 8 bytes per car in one branch-free loop that the compiler vectorizes (about 1.3 µs per tick at -O3, about 22x faster than the first struct-per-car version). Cost: cars cannot turn without moving between pools.
- **Cars ignore each other at crossings.** Cars on crossing roads drive through each other at intersections. Traffic lights would need queues and a following gap in every lane, which is far more code for a world that only feeds the camera. The overlap is a real tracking case: two boxes merge and split, and the tracker must keep their IDs (see the detection proposal).
- **Two kinds of config.** Settings that may change per run live in one file, `config/drone.ini` (INI: readable by Python's standard library and a 60-line C++ loader), and change without a rebuild: addresses, ports and FEC for both nodes, and the GCS's timing and slider settings in its `[gcs.*]` sections. The C++ loader ignores section names, so every key is unique. Wire-format facts (the UDP datagram maximum, the chunk payload size) and simulation constants stay in code (`constexpr` in `config.h`, named constants in Python), checked by the compiler.
- **GCS in tkinter, frames shown without Pillow.** OpenCV only decodes the JPEG; the frame goes to Tk as PPM (`cv2.imencode(".ppm")` into one reused `PhotoImage`), about 10 ms per frame, so no extra image library. tkinter gives real buttons and a slider, and each component lives in its own file: data goes in through `render(state)`, user actions come out through callbacks, and only the App changes the (immutable) state.
- **GPS behind an interface (Strategy + dependency injection).** The drone is constructed with a `GpsReceiver&` and refreshes its fix in its own update cycle (`Drone::Update` calls `UpdateGpsFix()`, which calls `ReadFix()`). The simulator injects a `SimulatedGpsReceiver`, an adapter over the `World`: it converts the drone's metres (x north, y east) to latitude and longitude around an origin in Be'er Sheva (flat-earth conversion, exact to centimetres over 1 km). A real receiver would be a `UartGpsReceiver` reading NMEA sentences from a serial port, with nothing else changing. Telemetry carries the receiver state as `GpsStatus`, a protobuf `oneof` (`fix` with lat/lon, or `no_fix`), protobuf's discriminated union, so "no position yet" is never confused with a real position; the GCS shows it in a GPS row. The drone updates before the world moves, so a fix is one tick (16.7 ms) old, like a real GPS.
- **No drone marker in the video; the GCS draws a crosshair.** The camera is always centred on the drone, so the simulator sends only the world (the assignment's example frame draws the drone as a yellow square; here nothing covers the cars under the drone, which also helps detection). The GCS draws a small crosshair with an open centre on a canvas above the frame. Overlays are separate components listed in `[gcs.ui] overlays` (empty for none), so a battery gauge or heading arrow can be added later as one more class.
- **GCS polls instead of using threads.** The Tk loop drains both non-blocking sockets every `poll_ms` (5 ms). No threads or locks, and it works on every OS. Cost: about 5 % CPU while idle (measured) and up to 5 ms extra delay, small next to the 33 ms between frames.
- **Commands carry a timestamp; the drone keeps the newest.** UDP can reorder datagrams, so each command carries `timestamp_ms` from the GCS wall clock (Unix epoch, uint64). `Drone::HandleCommand` ignores a command older than the last one it accepted and replaces `last_command` only on accept; equal timestamps apply, because the GCS can send twice in one millisecond (a stop right after a move). The drone only compares GCS timestamps with each other, so the nodes need no clock sync. Costs: the receiver still hands over only the last datagram of each 16 ms tick, so a newer command followed by an older one in the same tick loses until the next resend (100 ms); and there is no resync, so a GCS clock stepping backwards (NTP) makes the drone ignore commands until the clock passes the old time. A wall clock was chosen over a monotonic one so a restarted GCS needs no resync rule.
- **Commands are latched and resent.** An arrow latches a direction and the GCS resends the absolute velocity every 100 ms, so a lost command is replaced within 100 ms. While no telemetry arrives (link LOST) the resend interval doubles up to 1 s to keep a dead link quiet; any input or the link coming back returns to 100 ms. Closing the GCS sends a stop (`exit_stop_repeats`, 3 times, so one lost datagram does not leave the drone moving). The simulator is the real failsafe: when no valid command arrives for `command_timeout_ms` (optional in `[simulator]` of `drone.ini`; default 1500 ms from `kDefaultCommandTimeoutS` in `config.h`) the drone stops, so a crashed GCS or a dead link cannot leave it flying. The timeout is above `backoff_max_ms` (1000 ms) so the slow resend while LOST does not make the drone stop and restart; the cost is up to 15 m of flight after the GCS dies. It counts simulated time in `Drone::Update`, and `last_command` stays the last command accepted (speed 0 in telemetry shows the stop).
- **Restarts are detected, not configured.** A lower `frame_id` or `sequence` after more than `stale_ms` of silence (or a big drop) means the simulator restarted; the GCS resyncs and keeps its statistics across runs.
